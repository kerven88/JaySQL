记录谁在什么时候对什么做了什么，含变更前后的数据快照，用于合规检查与事故溯源。

## 操作日志

| 字段 | 说明 |
| --- | --- |
| 操作人 / 时间 | 谁、什么时候 |
| 模块 / 动作 | 做了什么类型的事 |
| 目标对象 | 实例、任务、工单等 |
| 变更前 / 变更后 | **数据快照**，用于对比 |
| `request_id` | 与访问日志、查询记录串联的钥匙 |

### 溯源方法

拿到一条审计记录后：

```text
request_id
  ├─ 请求日志（*-request.log）→ 完整 URI、耗时、来源 IP、UA
  ├─ 审计记录 → 变更前 / 变更后快照
  └─ 查询记录 → 实际执行的 SQL 与影响行数
```

排查一次误操作时，用 `request_id` 一条线就能把「谁、从哪、多久、改了什么」全串起来。

## 策略配置

- 配置需要重点审计的动作、保留策略与告警联动
- 数据访问授权变更、权限变更、备份任务删除等高危动作建议全部纳入

:::warn 已知盲区：登录行为
当前**登录行为没有完整的审计落库**，只有用户表上的最后登录时间字段。
如果需要"谁在什么时候从哪里登录失败过几次"这类合规证据，需要额外埋点。
:::

## 保留与清理

审计日志**默认不做自动清理**，只增不删。数据量上来后建议：

1. 确定保留期（如 180 天 / 1 年，按合规要求）
2. 到期数据**先归档备份再删除**
3. 删除用**分批 DELETE**，不要一次性大事务：

```sql
-- 分批删除示例，反复执行到影响行数为 0
DELETE FROM insight_audit_logs
WHERE created_at < DATE_SUB(NOW(), INTERVAL 180 DAY)
ORDER BY id
LIMIT 10000;
```

:::danger 删除前必做
先备份（`mysqldump --single-transaction`），并在事务里小批量执行、逐批确认影响行数。
审计数据删了就补不回来，合规检查时拿不出来是硬伤。
:::
