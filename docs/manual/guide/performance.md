从「现在慢不慢」到「慢在哪条 SQL」再到「当时发生了什么」，形成闭环。

## 性能概览

按实例汇总关键指标趋势（QPS / TPS、连接数、慢查询数、锁等待），用于快速判断是否存在异常波动。

<!-- screenshot: 性能概览趋势图 -->

:::info 数值对不上？（压测 100 QPS，页面只显示 20~30）
按四段定位，**不要一上来就怀疑采集**：

1. **先证伪客户端口径**——压测工具的 QPS 是否含连接建立、是否复用连接、是否统计了失败重试
2. **再查连接层**——连接池上限、是否走了代理、实例端 `Threads_connected` 是多少
3. **再查采集管道**——采集周期是多少、采集时刻是否与压测窗口对齐、有没有采集失败
4. **最后查指标定义**——页面上的 QPS 是"每秒查询数"还是"每秒事务数"，口径是否与你理解的一致
   :::

## 慢 SQL

### 采集

采集器按实例配置**阈值**与**采集周期**，定时抽取慢日志并入库。参数在系统配置中调整。

### 列表字段

| 字段 | 用途 |
| --- | --- |
| 指纹 | 归一化后的 SQL 模板，用于聚合（同一模板的不同参数会归到一起） |
| 执行次数 / 总耗时 | 判断影响面——次数多但单次快的，往往比单次极慢的更值得先治 |
| 平均 / 最大耗时 | 判断抖动——最大远大于平均，说明有偶发劣化 |
| 扫描行数 / 返回行数 | 判断索引效率——扫描远大于返回，基本就是索引问题 |

### 治理动作

1. **改写 SQL**——去掉不必要的排序、子查询、函数包裹的索引列
2. **补索引**——按执行计划的 `key` 与 `rows` 判断
3. **调参数**——如 `sort_buffer_size`、`tmp_table_size`（谨慎，先评估全局影响）
4. **验证**——在 [SQL工作台](./sql-workbench.md) 用只读方式对比改写前后

## 负载快照

在故障或压测时**手动触发**，抓取当时的会话、锁、状态变量等形成报告，事后再看仍有据可查。

- 快照参数（抓取项、保留天数）可在系统配置调整
- 报告页可查看快照时间、实例、各项指标明细
- 建议：**故障当下先抓快照，再去查原因**——很多现场信息事后无法复现

:::tip 什么时候抓快照
- 业务反馈"刚才卡了一下"，但等你登录时已恢复
- 压测过程中想留存中间态
- 准备做大变更前留一份基线
  :::
